# Milos Beach Data Verification — Filter & Display Attributes

**Date:** 2026-06-15
**Scope:** All 42 Milos beaches (ids 1898–1938, 3000). Static filterable/displayed attributes only.
The geometry-derived wind-exposure / orientation / `protectedFrom` model was **out of scope** by
agreement (it has its own validator, `scripts/validateWindExposureGroundTruth.mjs`).
**Mode:** Verification report. **Update 2026-06-15:** after review, the four high/medium-confidence
Milos data fixes below were **applied** to `public/greek_beaches.json` and rebuilt (see
"Update — corrections applied"). The systemic and low-confidence items remain open.

> **Source of truth:** `public/greek_beaches.json` (region → prefecture → beaches). The
> `public/data/beaches/.../south-aegean-milos.json` files are generated by `npm run build:beach-data`.
> Any correction below must be made in `greek_beaches.json` and then rebuilt — never edit the
> generated files.

The Milos dataset is **in good shape**. It has already been through several sourced audit passes

verification surfaced **one factual error, one data gap, a handful of judgment-call / minor issues,

filter or card shows.

## Methodology

**Layer 1 — automated audits (scoped to Milos), all run on 2026-06-15:**
- `node scripts/auditBeachFilterAttributes.mjs south-aegean-milos` → 42 beaches, **1 high finding**
  (Kleftiko missing `metadata.waterDepth`). Everything else internally consistent.
- `node scripts/auditAmenitiesOsm.mjs --region south-aegean-milos --radius 800` → **0/42 flagged**;
  OSM food POIs corroborate the organized beaches (see `.tmp/milos-amenity-audit.csv`).
- `npm run audit:place-resolution -- --island=milos` → **PASS=3, REVIEW=0, FAIL=0** (only the 3
  name-routed beaches are in scope; the rest are coordinate-routed and were not contested).
- Cross-checked the filter-deriving code paths in `services/recommendationService.ts` and
  `scripts/buildBeachRegionData.mjs`.

**Layer 2 — web research** (cross-checking ≥2 sources for contested attributes): official Blue Flag
2026 coverage, Municipality-of-Milos Seatrac announcement, and travel sources for the high-signal
beaches (Sarakiniko, Papafragas, Pollonia, Tsigrado). Minor/low-profile beaches were verified through
the Layer-1 OSM + place-resolution audits plus their existing multi-source provenance in
`sourceNotes`, rather than an individual web search each.

**How attributes reach the UI (verified):** the user-visible filter chips are
`blueFlag2026, disabledAccess, sandy, pebbles, quiet, beachBar, easyAccess, snorkeling,
familyFriendly, deepWater, shallowWater` (quick) and `naturalShade, taverna, sunbeds, parking,
sandy-pebbles, rocky, adventure` (advanced). Each chip's data field and the derivation that feeds it
were confirmed in `services/recommendationService.ts`, `utils/access.ts`, and the build script.

## Key findings

### ❌ 1. Sarakiniko (id 1922) — beach type overstates sand
- **Current:** `terrain.types = ["rocks","fine_sand"]` → derived **`beachType = sandy-pebbles`**.
- **Reality:** Sarakiniko is the iconic white **volcanic-rock "moonscape"**; sources agree there is
  "only a tiny narrow strip of sand nestled between the cliffs" / "very little sand." It is
  fundamentally a **rocky** swim/snorkel/cliff-jump spot, not a sand-and-pebble beach.
- **Filter impact:** `sandy-pebbles` also matches the **"Sandy"** quick filter, so a user filtering
  for sandy beaches gets Sarakiniko — misleading for families expecting sand. It does *not* appear in
  the **"Rocky"** advanced filter, where it belongs.
- **Proposed:** set `terrain.types = ["rocks"]` (→ `beachType = rocky`), or `["rocks","pebbles"]` if
  you want to keep some granular surface. Keep `snorkeling` (rocky terrain already drives it).
  *Confidence: high on "primarily rocky"; the exact terrain array is a judgement call.*

### ❌ 2. Kleftiko (id 3000) — missing water depth (audit-flagged)
- **Current:** no `metadata.waterDepth` → `auditBeachFilterAttributes` raises `missing_metadata_water_depth`.
  Top-level `waterDepth`/`characteristics` are therefore empty, so Kleftiko is absent from both the
  **Deep water** and **Shallow water** filters and the depth line on its card is blank.
- **Reality:** Kleftiko is a deep sea-cave bay you swim into from a boat — clearly **deep water**.
- **Proposed:** add `metadata.waterDepth = { type: "deep", label: "βαθιά νερά" }`.
  *Confidence: high.*

### ⚠️ 3. Pollonia (id 1932) — sunbeds available but not listed
- **Current:** `organized = true`, `amenities = ["ταβέρνες κοντά","καφέ κοντά","parking κοντά"]`. The
  `sunbeds` flag derives from *organized AND a sunbed term in the amenities list*, so with no sunbed
  term it computes **`sunbeds = false`**.
- **Reality:** sources confirm parts of Pollonia are organized **with sunbeds + umbrellas** (run by
  the beachfront cafés/tavernas), plus tamarisk shade.
- **Filter impact:** Pollonia is wrongly excluded from the **"Sunbeds"** advanced filter.
- **Proposed:** add `"ομπρέλες εποχικά"` / `"ξαπλώστρες εποχικά"` to the amenities list.
  *Confidence: medium-high.*

### ⚠️ 4. Papafragas (id 1916) — type / access / "quiet"
- **Type:** `["rocks","fine_sand"]` → `sandy-pebbles`. It is a **~5 m sand pocket inside sea caves**,
  overwhelmingly rock. Same "shows up under Sandy" concern as Sarakiniko, though milder (there *is* a
  real, if tiny, sandy patch). *Consider `rocky`.*
- **Access:** `hiking_path_easy` (you corrected this on 2026-06-15 to "good road + short careful foot
  descent"). Travel sources still stress a **steep, slippery, narrow descent with "swim at your own
  risk" warning signs**. The current access *notes* keep that caution, so this is consistent — flag is
  only to confirm "easy" is the label you want for the chip logic (it maps to MODERATE, not EASY, so
  it stays out of "Easy access"; that's fine).
- **"Quiet":** derived `quiet = true` (from absence of service amenities), but Papafragas is a busy,
  much-photographed stop. Consider disabling `quiet` (as was done for Tsigrado on 2026-06-05).
  *Confidence: medium.*

### ⚠️ 5. NE "unknown-access" beaches — Kastanas (1935), Kolympisionas (1936), Rema (1937), Tria Pigadia (1938)
- **Current:** `access.type = "unknown"` → derived `accessibility = MODERATE`; notes honestly say
  access is unverified.
- **Issue:** "MODERATE" implies a walkable approach the sources don't actually confirm; these are
  remote NE coves near the mining coast often reached by boat. They correctly stay out of "Easy
  access," and the card label is honest, so impact is low — but the MODERATE default is an assumption,
  not a verified fact. *No change required; listed for transparency. If anything, several may be
  boat/limited access.*

### ⚠️ 6. Provatas (id 1920) — possible accessibility ramp not captured
- greeka's sea-ramps guide names **Provatas** as having a "SeaAccess" ramp (a *different* brand from
  Seatrac). The current 2026 Municipality-of-Milos announcement lists only Papikinou, Plathiena,
  Pollonia — not Provatas. We mark Provatas as not accessible.
- **Impact:** possible false-negative on the **Accessible** filter, *or* greeka is outdated. Given the
  authoritative municipal source omits Provatas, leaving it unmarked is defensible. *Worth a direct
  check before next season. Confidence: low.*

### ⚠️ 7. Voudia (id 1934) & deep-entry on rock coves — low-confidence notes
- **Voudia:** `asphalt_road`, pebbles/rocks, deep. It sits by the industrial mining loading port;
  road access is plausible but it is an industrial-adjacent swim spot — keep an eye on whether it
  should be surfaced as a normal beach. *Confidence: low; no clear error.*
- **Deep-water rock coves** (e.g. Sarakiniko, Agia Kyriaki): classed `deep`, which is right for the
  open water but several "deepen gradually from a shallow shore." This only affects which of
  Deep/Shallow they appear under; current `deep` is acceptable.

## Systemic findings (apply to all Greek beaches, surfaced via Milos)

### 🟡 A. `surfing` is a synthetic id-hash (latent)
`activities.surfing = surfingOverride ?? (getDeterministicValue(id,'surfing') > 0.8)`
(`scripts/buildBeachRegionData.mjs:527`). No Milos beach has a real surfing override, so the flag is a
**deterministic hash of the beach id** — pure noise. It currently marks 6 Milos beaches as surfing,
including the calm, family-friendly **Plathiena**.
- **Why it's only "latent":** `surfing` is **not exposed as any filter chip** (it's absent from
  `QUICK_PREFERENCE_FILTERS` and `desktopAdvancedFilters`) and isn't shown on the card, so users can't
  currently act on it. But the field exists, feeds `beachMatchesUserPreferences`/scoring
  (`recommendationService.ts:373,1601`), and would be wrong the moment it's surfaced.
- **Proposed:** either stop emitting a synthetic `surfing` value (default `false` unless a metadata
  override exists), or keep it explicitly unused. *Not Milos-specific.*

### 🟡 B. `rating` is a synthetic id-hash (displayed + sortable)
`rating: 4.0 + getDeterministicValue(id,'rating') * 1.0` (`buildBeachRegionData.mjs:495`) — every
beach gets a fabricated 4.0–5.0 score. This **is shown on the card** and is a **sort option**
("Top-rated"), so the rating users see and the "top-rated" ordering are not real. Same for
`popularityScore`. Systemic and likely a known placeholder, but worth a decision since it's displayed.

**Navigation fix (Google Maps "open in maps") — applied 2026-06-15.** User testing surfaced that
Milos beaches navigated by **name** mis-resolved or returned nothing on Google Maps: Κάτεργο →
Folegandros, Ψαθί → Kimolos, Φυρλίνγκος → no result. Root cause: 39/42 Milos beaches were
`place`-routed (name query), and Milos names collide heavily across the Cyclades (Άγιος Ιωάννης
appears on 11 islands, Άγιος Σώστης on 7) or are too obscure for Google. Fix: routed **all 39
name-routed Milos beaches by coordinate pin** (`googleMapsNavigation.mode = "coordinates"`,
collision-immune per `utils/navigation.ts`); the in-app Leaflet map already used these (validated)
coordinates, so only the external link was wrong. The 3 beaches with hand-verified island-qualified
queries (Παλαιοχώρι, Προβατάς, Σαρακήνικο — e.g. `"Sarakiniko beach, Milos, Greece"`, Nominatim-
confirmed 0–320 m from pin) were left as `place` (richer Google card, resolve correctly).

**Nationwide rollout — applied 2026-06-15.** The same collision/non-resolution class affects every
island (e.g. «Άγιος Ιωάννης» appears on 11 islands), so the fallback policy was fixed once in code:
`utils/navigation.ts` `getDirectionsDestination` now routes by **coordinate** (collision-immune)
whenever there is no hand-verified explicit `query`, instead of a bare `"<name>, <island>"` query.
This supersedes the prior place-first default for unaudited beaches (the 2026-06-12 contract; the
`navRegressionSnapshot` baseline was re-saved and its header updated). Result across all 2745
beaches: **0** route by bare name — 2741 route/locate by coordinate, 4 keep their verified explicit
query. Verified: `tsc` clean, `navValidation` 11/11, nav regression hard-gate PASS (1322 ABSENT
beaches, 0 URL diffs).

**Still open** (not applied): the two systemic items (#5 `surfing`, #6 `rating`) need an
all-islands decision, and the low-confidence items (#7 Provatas ramp, #8 NE unknown-access) need
external verification before any change.
